# Bellhaven reconciliation

The pipeline found 35 communities across all three directory pages and the homepage. Findlay appears only in the homepage announcement, so trusting the directory's count of 34 would miss a real acquisition. All 121 initial CRM accounts were searched, including accounts under other operators and independent facilities.

Matching starts with normalized street addresses, city and state, with ZIP and name as corroboration. Equivalent abbreviations do not trigger daily updates. Exact names with matching locality can support corrections such as Ashtabula's PO box; names alone are insufficient. The unrelated Colorado Springs Amberly Manor was rejected as a match for the Hudson, Ohio community. For multiple address-backed candidates, deterministic ranking selects a proposed survivor; all alternatives remain visible for review. Scores express rule strength rather than calibrated probability.

The local app shows source evidence, the original CRM record, financial exposure and the proposed field differences. A decision note is required. Only approval writes through the API; rejection is recorded locally. Before every write, the app refreshes the account, checks for stale evidence and verifies the resulting record. No accounts are deleted or merged. Seven duplicate copies were marked Inactive with survivor pointers and explanatory notes. Three unlisted Bellhaven accounts were marked Needs Review while preserving their parent and financial data: absence from the website does not prove a sale or closure.

The billing rule is enforced at approval time. Tiffin and Marietta have both revenue history and positive outstanding AR, so new Bellhaven accounts were created and only the old accounts' CHOW pointers were changed. The old accounts' other fields were compared against the initial snapshot and preserved. Findlay and Lima could be re-parented directly because their AR was zero. Four genuinely missing locations were created: Amberly Manor in Hudson, Union Square at 118 Union Square Drive, Batavia and Carlisle.

The final CRM contains 127 accounts and exactly one current active Bellhaven account for each of the 35 website communities. There are 31 approvals and two rejections, including two optional formatting reviews used in the demonstration: one equivalent address spelling was accepted, another rejected. A fresh daily run produced zero new or pending proposals. Stable decision IDs, SQLite persistence, a local lock and a create-operation journal make reruns safe. A marker supports recovery after a partial create; an uncertain POST is not blindly retried. Twenty automated tests cover the key matching, billing, recovery and decision-persistence cases.

AI assistance was used extensively for implementation, test design, interface iteration and browser-operated review. The checks were deterministic tests plus actual API read-after-write verification, not an assumption that generated code was correct. The application itself makes no LLM calls and needs no paid API key. The narrated demo uses synthesized speech over actual browser captures.

Next I would add corroborating ownership sources for the unlisted facilities, authenticated multi-reviewer access, database backups and notifications, and server-side idempotency and conditional writes. The present API cannot make the preflight GET and update atomic, so a narrow race with an external CRM writer remains. The supplied cron configuration generates proposals daily without automatically approving them.
